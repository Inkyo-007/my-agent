# 后端设计说明

本目录按功能层组织后端的设计文档：**一层一份**，说明该层的内容、职责与设计方案。

## 阅读指引

- **想快速了解某一层是干什么的**：看对应文档的「定位与职责」一节；
- **要改动或使用某一层**：除「定位与职责」外，重点看「如何扩展/接入」与「测试方式」类的小节；
- **对某个设计不理解**：每层文档会解释关键设计背后的理由，而不仅是结论。

阅读顺序上没有先后依赖，但从 [core.md](./core.md) 开始最顺——其他层都建立在它定义的基础类型之上。

其余功能层（security、memory、mcp、reliability、orchestration）仍在规划中，实现后按同样方式各补一份，并在此处更新文档清单。

## 重要约定

- 每层一份文档，文件名与层名一致（如 runtime 层对应 `runtime.md`）；
- 与代码同步更新：层的职责或关键设计发生变化时，同一次变更中更新对应文档；
- 各层通用的编码规范不在此重复，见开发规范文档（`docs/rules/`）。

## 写作风格

- 一律使用中文；通用术语与代码标识符保留英文原文。
- 设计文档面向人类开发者写作，使用平实的表述，像给同事讲解一样说明设计，而不是罗列类型签名；避免自造的说法，不常见的概念首次出现时用一句话解释。

## 参考内容结构

每份设计文档建议包含以下小节（按需取舍，顺序不限）：

1. **定位与职责**：这一层负责什么、不负责什么，边界比功能罗列更重要；
2. **文件一览**：层内各文件承担的内容；
3. **关键设计**：重要的设计方案**及其理由**——读者最需要的是「为什么这么做」，只有结论没有理由的文档对后来者的帮助有限；
4. **使用与扩展方式**：如何接入一个新的实现（如新模型服务、新工具）；
5. **已知边界**：当前方案明确不覆盖的场景与触发升级的条件（如有）；
6. **测试方式**：该层的测试策略与打桩约定。

注：以上内容为参考结构，具体小节可根据实际情况增减，顺序也可调整。
