# core — 基础定义层

## 定位与职责

core 是整个系统最底层的共享定义层：消息格式、工具接口、事件广播、模型调用契约等被多个功能层共同需要的基础类型，都定义在这里。

它的职责边界有两条硬规则：

- core 不依赖任何其他层，其他所有层只依赖 core；
- 只服务于某一层的类型不属于这里。判断标准很简单：这个类型是否被两个以上的层共同使用？是，放 core；否，放对应功能层。

core 基本只包含**定义**（契约与数据类型），不实现任何功能逻辑——怎么调模型 API（models 层）、怎么执行工具（tools 层）都不归它管。唯一的例外是与契约共生的小工具（如 `EventEmitter`）：它被多个功能层共同使用、只依赖 core 类型，按依赖方向只能放在这里。

## 文件一览

| 文件 | 内容 |
|---|---|
| `agent.py` | Agent 的定义、状态枚举（`AgentState`）、执行结果（`ExecutionResult`） |
| `message.py` | 应用层消息（`Message` 及其子类），含序列化能力 |
| `event.py` | 事件（`Event`、`EventType`）、事件总线接口（`EventBus`）与发射助手（`EventEmitter`） |
| `tool.py` | 工具接口（`Tool`）、工具定义与调用、执行结果的统一类型 |
| `provider.py` | 模型调用契约（`BaseProvider`）与协议层消息格式 |

## 消息体系（message.py）

`Message` 是应用层的通用消息：无论是用户输入、模型回复还是工具结果，都包装成 `Message`，携带角色、类型、内容、思考文本、id、时间戳与元数据。

两个值得注意的设计：

- **子类通过元数据访问器扩展**：`ToolCallMessage`（工具调用）与 `ToolResultMessage`（工具结果）不新增存储字段，而是把工具调用列表、执行状态放在 `metadata` 里，用只读属性（`tool_calls`、`is_success` 等）提供类型化的访问入口。消息结构保持稳定，扩展不破坏存储格式。`tool_calls` 的存储格式为 `[{"id", "name", "input"}, ...]`，一次模型响应可能携带多个工具调用，单次调用即长度为 1 的列表。
- **序列化往返不丢类型**：`to_dict()` / `from_dict()` 支持完整的往返，`from_dict()` 会按存储的 `type` 字段还原出正确的子类（否则存盘再读回，子类会退化成基类，属性访问器全部失效）。这是为将来的会话持久化铺的路。

`thinking` 字段记录模型的思考内容——它是用户可见的产品功能（UI 展示、审计），所以进 `Message`；而思考签名这类纯协议细节不进，见下节的边界划分。

## 两套消息模型的分工

系统里有两套消息类型，容易困惑，这里集中说明：

- **`Message`（message.py）——应用层**。面向产品功能：id、时间戳、元数据、序列化。由运行时、记忆、UI 等模块消费。
- **`ProviderMessage`（provider.py）——协议层**。面向模型 API：携带协议保真所需的字段（思考签名、加密思考数据、工具调用配对）。由 models 层消费。

两套模型不合并的原因：它们的读者和变化原因不同。合并会让应用层的消息模型被协议细节污染（每个字段都要回答「这个字段是干嘛的」），拆开则各自清爽。两者之间的转换由将来的运行时层负责。

## 工具接口（tool.py）

定义了工具的完整契约家族：

- `Tool`：抽象基类，所有工具实现它，必须提供 `definition` 属性与异步的 `call()` 方法。`definition` 的合法性不在定义时检查，而在注册进注册表时检查（tools 层负责）。
- `ToolDefinition`：工具的自我描述——名字、说明、参数 schema、权限标签、超时时间。
- `ToolCall` / `ToolResult`：一次工具调用的输入与输出。`ToolCall.input` 永远是字典（各家 API 的差异在 models 层被吸收）。
- `HookVerdict`：执行钩子的裁决结果——放行或拦截。它与 `ToolResult` 同属「工具执行的反馈」：`ToolResult` 是执行之后的结果，`HookVerdict` 是执行之前的放行裁决。
- `BaseToolExecutor`：工具执行器契约，只承诺一个行为——`execute(tool_call) -> ToolResult`。runtime 等编排层只依赖这个接口，不认识具体实现；流水线细节（校验、钩子链、超时、事件发射）由 tools 层的 `ToolExecutor` 实现承担。

**权限标签公约**：`permission_required` 是字符串列表，格式约定为 `"{领域}:{动作}"`，如 `fs:read`、`fs:write`、`shell:execute`。声明是静态事实（这个工具会碰什么），策略判断（这次调用放不放行）由执行钩子负责。用字符串而非枚举是有意的：领域会不断生长，字符串不需要为此改动 core。

## 事件（event.py）

`Event` + `EventType` 定义了运行时对外广播的事件（任务开始/结束、步骤、工具执行、权限审批等），`EventBus` 是事件总线接口：

- 发布者只管发，不关心谁在听；订阅者自行过滤感兴趣的类型；
- 实现方必须保证：单个订阅者抛异常，不影响其他订阅者和发布者；
- 事件只承载「通知」。需要回答的场景（如「这个操作放不放行」）不走事件，走执行钩子——事件没有返回值，表达不了裁决。

发射一侧由 `EventEmitter` 收口：tools、runtime、security 等相互独立的功能层都需要发射事件，这段共用的样板按依赖方向只能收敛到 core。它的职责固定为三样——总线为 None 时静默（事件是通知、不是刚需）、打上发射方的 source 标签、构造 `Event` 并发布；过滤、批处理、异步投递等都不属于它。各编排类在构造时把可选的总线包装成 `EventEmitter`，之后只管调 `emit()`。

## 模型调用契约（provider.py）

`BaseProvider` 是所有模型 Provider 的抽象基类。两个关键约定：

- **它只承诺行为，不规定构造**：接口只有 `complete()`（非流式）和 `stream()`（流式）两个方法，刻意不定义 `__init__`——需要什么配置、怎么创建连接，是实现自己的事。两个方法都是异步的：`complete()` 是协程，`stream()` 返回异步生成器（调用方以 `async for` 消费事件）——agent 循环是异步编排，契约与之一致。
- **流式事件格式是固定约定**：`StreamType` 五种事件（开始、正文增量、思考增量、工具调用增量、结束），每种事件的 `delta` 字典字段有明确约定（见 `StreamProviderResponse` 的文档字符串）。最重要的一条不变量：**STOP 一定是流的最后一个事件，且携带完整的 token 统计**。

## 设计约定

- **接口与其核心数据类型放在同一文件**：事件总线接口和事件类型同居 `event.py`，钩子裁决和工具结果同居 `tool.py`。小而相关的概念就近放一起，读者单文件就能读完一个完整的故事；文件大到臃肿了再拆。
- **core 求稳不求全**：它是所有层的公共依赖，任何改动都会波及全局。新增内容前请先确认它真的是跨层共享的，且没有更合适的归属。
