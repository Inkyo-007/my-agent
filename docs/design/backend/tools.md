# tools — 工具执行层

## 定位与职责

tools 层负责工具的注册、校验与执行。理解本层的关键是**机制与内容的分离**：

- **机制**（本层现有的内容）：注册表、参数校验器、执行器——一套与具体工具无关的框架；
- **内容**（将来补充）：具体的工具实现（读文件、执行命令、网络搜索等），计划放在 `tools/builtin/` 子包。

名字 `builtin` 是刻意的：这些只是「预装内容」，地位与将来从 MCP 适配来的、用户自行添加的工具完全平等，都走同一套注册与执行机制。纯问答场景的 Agent 甚至可以不装任何工具。

## 文件一览

| 文件 | 内容 |
|---|---|
| `registry.py` | `ToolRegistry`：工具的注册、注册时校验、按名查找 |
| `validator.py` | 机械校验（存在性、参数 schema），纯函数、无状态 |
| `executor.py` | `ToolExecutor`：执行流水线，含执行钩子与事件发射；实现 core 的 `BaseToolExecutor` 端口 |
| `builtin/` | 预装工具（内容层）：`fs.py` 含 `read_file` / `write_file`，`shell.py` 含 `shell_command`，约定见「内置工具」一节 |

三者的分工：注册表只管「存与取」，校验器只管「确定性检查」，执行器负责把各环节编排成流水线。任何一环的具体规则都不混进其他环节。

执行器的调用契约（`execute(tool_call) -> ToolResult`）以 `BaseToolExecutor` 的形式定义在 core：runtime 等编排层只依赖该端口，本层是唯一实现方。端口只承诺「执行一次调用并返回结果」，钩子链、超时、事件发射等都是本层的实现细节，不进契约。

## 执行流水线

`ToolExecutor.execute()` 是核心入口，一次调用走四步：

1. **存在性检查**：工具不存在 → `error_type="tool_not_found"`，错误文案附相近名字的模糊建议和可用工具清单；
2. **参数校验**：按工具的 schema 检查必填项与类型 → `error_type="invalid_input"`；
3. **钩子链**：逐个 await 异步钩子，首个非放行裁决即短路 → `error_type="permission_denied"`；
4. **执行**：带超时控制调用工具，异常兜底 → `error_type="timeout"` / `"execution_error"`。

贯穿全程的两条规则：

- **永远返回 `ToolResult`，不向调用方抛异常**。失败也是结果——Agent 循环需要把失败喂回模型让它自我纠正，异常会打断这个循环；
- **`error_type` 是稳定契约**，只有上述五个取值，供 UI、审计、循环分类消费；给模型看的可读文案放在 `content` 里。

**错误文案是写给模型看的**：文案会被原样喂回模型，所以它必须具体、可操作——说清楚错在哪、可以怎么改，模型才能得体地向用户解释或纠正重试，而不是盲目重试。模糊建议（「您是想要调用 'get_weather' 吗？」）就是为此服务的。

## 执行钩子：安全能力的挂载点

钩子的类型是 `Callable[[ToolCall, ToolDefinition], Awaitable[HookVerdict]]`——任何符合这个签名的异步可调用对象都是合法实现。异步签名是审批场景的硬需求：等待用户裁决（终端确认、Web 弹窗）不能阻塞事件循环。安全防护层（security）会以钩子的形式接入，本层不感知它的存在。

语义约定：

- 空钩子链 = 全部放行；
- 裁决是三态（`HookDecision`）：放行继续后续钩子，拦截（`DENY`）短路失败，待审批（`ASK_USER`）按拒绝兜底并附注「审批通道未接入」——审批通道由 security 在钩子内部解决，执行器不直接面对用户；
- 拦截是**正常业务流程**（比如用户拒绝了一次危险操作），不是异常；拦截理由会被包装进结果喂回模型，让它能向用户解释，而非盲目重试。

## 事件发射

执行器在「开始 / 成功 / 失败」三个时点发射事件，发射经由 core 的 `EventEmitter`（构造时传入的总线包装而成）：总线是可选的，不传入就完全静默；发射方身份（source 标签）也由它统一打上。将来接入日志、追踪等可观测性能力时，只需在总线侧新增订阅者，执行器零改动。

事件内容的约定：**事件是通知，不是数据搬运**。content 只放摘要文案（如「工具 read_file 执行成功」），工具结果的截断摘要（上限 500 字符）放在 `metadata.result_excerpt` 供 UI 预览；完整结果在 `ToolResult` 与 history 中，不随事件广播——否则 read_file 的数千行输出会被迫送达每个订阅者。同理，分隔线、缩进等排版是订阅者自己的事，不混进事件内容。

## 如何新增一个工具

1. 继承 core 的 `Tool`，提供 `definition`（名字、说明、参数 schema、权限标签、超时）与异步的 `call()` 方法；
2. 在应用入口处注册进 `ToolRegistry`。

注册时会被校验的内容：`definition` 必须是合法的 `ToolDefinition`、名字与说明非空、参数 schema 类型正确、**不允许同名覆盖**（后注册者悄悄顶替先注册者是配置错误，必须暴露而不是吞掉）。

注意两点约定：

- **权限标签要保守诚实**：可能写就必须声明 `write`，宁可多声明。声明是给安全钩子看的静态事实，漏报等于绕过安全检查；
- **路径/命令参数用 `format` 标注**：接收文件路径的参数声明 `"format": "path"`，接收 shell 命令的参数声明 `"format": "command"`——这是 JSON Schema 的标准注解关键字，校验器不传 format checker 时会忽略它（不影响参数校验），security 用它声明式提取待检路径与待分析命令，该标注也随 schema 发给模型；
- **工具发现采用显式注册**：在入口处逐个 `register`，不做目录扫描式自动发现。显式注册让「这个 Agent 带了哪些工具」一目了然；自动发现等真实需求出现再考虑。

## 内置工具（builtin/）

机制与内容分离的「内容」一侧。这里只是预装工具，地位与将来从 MCP 适配来的、用户自加的工具完全平等。当前包含 `read_file`（`fs:read`）、`write_file`（`fs:write`）与 `shell_command`（`shell:execute`）。

所有内置工具必须遵守的约定：

- **路径解析，不做边界检查**：工具构造时注入 `root_dir`，相对路径基于它 resolve（含符号链接）。围栏已上移 security——执行器集成落地后，路径内/外由 security 统一裁决（工作区外经审批放行），工具只负责忠实执行。
- **输出截断**：`read_file` 单次默认最多返回 2000 行（可用 `offset`/`limit` 分页），截断时在结果中明确标注总行数与已显示范围——模型需要知道有截断才能决定下一步。
- **失败即结果**：文件不存在、非 UTF-8、非零退出码、shell 启动失败等都返回 `ToolResult(success=False)` 加具体文案，不抛异常（executor 契约）。
- **权限标签保守诚实**：见「如何新增一个工具」。

`shell_command` 的两点特殊设计：

- **方言无关**：工具不感知 bash / pwsh 差异，只按注入的 `ShellProgram`（可执行文件 + 参数模板）拼接调用——避免 tools → security 的依赖（方言枚举在 security），探测与映射在 application 层（`shell_env.py`）；definition 是实例属性，描述中告知模型当前方言，模型据此写出语法正确的命令；
- **安全裁决全部上移**：工具自身不设任何护栏——危险命令硬阻断、工作区外 cwd 审批都由 security 在执行前完成（`command` 标注 `format: "command"`、`cwd` 标注 `format: "path"`）；执行器超时经取消传达时，工具负责杀掉子进程，避免进程泄漏。

## 测试方式

- 注册表与校验器是普通单测：构造内存中的注册表与虚拟工具即可；
- 执行器测试覆盖流水线的每个分支：成功、四类失败、钩子否决与短路、ASK_USER 泄漏兜底、事件序列、无事件总线时的静默。耗时与异常通过可控的 `StubTool` 模拟（`delay` 参数触发超时，`error` 参数触发内部异常）；
- 事件总线用收集型测试替身（`CollectingBus`）断言事件序列与元数据；
- `shell_command` 真实拉起子进程验证输出捕获、退出码、cwd 解析与取消回收，本机没有对应 shell 时跳过（探测逻辑在 application 层另有离线测试）。
